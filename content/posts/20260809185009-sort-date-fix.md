# 折腾小记：网站文章排序不对，原来是日期字段被统一改写

上一篇刚把思源里的顺序捋直，用户回头一看网站首页：怎么黑边帖又跑到圆角帖上面去了？按创建时间，圆角（17:40）应该排在黑边（16:00）前面才对。查了一轮，发现又是 sync 管线的锅——这次藏得比上次还深。

## 现象

网站首页顺序：黑边帖 → 圆角帖 → 新帖。

用户要的是按创建时间排：圆角应该在黑边上面。但 Hugo 是按文章的 `date`​ 字段排序的，`date`​ 是从哪来的？来自 sync 脚本。

## 弯路一：以为 date 是对的

先看生成的文章 frontmatter：

```toml
# 黑边帖
date = "2026-08-09T17:50:06+08:00"

# 圆角帖
date = "2026-08-09T17:50:06+08:00"
```

两篇的 date 一模一样——都是 17:50:06。这不是巧合，是 sync 管线把两篇的日期写成了同一个值。

## 根因：sync 用「更新」时间冒充「创建」时间

sync 脚本生成 frontmatter date 时，取的是思源 `.sy`​ 文件的 `updated`​ 字段。而这个字段在 API 创建文档时被统一写成了创建时刻——两篇都是同一秒创建，updated 自然相同。

Hugo 排序遇到相同 date 时退化为按文件名排：`20260809160000-black-edge-fix`​ < `20260809174000-corner-bug`​，黑边帖就排到了前面。看着像「按文件名排序」，实则是 date 失效后的兜底行为。

## 修法：date 优先取 slug 时间戳

好消息是每篇文章的 `slug`​ 字段（自定义 URL 的后半段）里编码了真实发布时间：`20260809160000-black-edge-fix`​ 的 16:00、`20260809174000-corner-bug`​ 的 17:40。

所以把 sync 脚本改成：**date 优先取 slug 前 14 位时间戳，没有 slug 才退回 updated**。

```python
slug = props.get('slug', '')
ts = ''
if len(slug) >= 14 and slug[:14].isdigit():
    ts = slug[:14]  # slug 编码的就是真实发布时间
elif updated:
    ts = updated
dt = datetime.strptime(ts, '%Y%m%d%H%M%S')
date_str = dt.strftime('%Y-%m-%dT%H:%M:%S') + TZ
```

改完删掉旧生成的 md 强制重转，三篇的 date 各归各位：

```text
黑边帖   2026-08-09T16:00:00+08:00
圆角帖   2026-08-09T17:40:00+08:00
排序帖   2026-08-09T18:00:00+08:00
```

首页顺序立刻变成：排序帖 → 圆角帖 → 黑边帖，圆角终于回到了黑边上面。

## 经验

- <strong>「更新时间」不等于「创建时间」</strong>：任何同步管线拿 updated/mtime 当发布时间都会埋雷，批量导入时尤其容易集体撞车。
- **slug 里编码时间戳是个好习惯**：URL 稳定 + 排序依据 + 人类可读，一石三鸟。
- **Hugo date 相同时的排序是退化的**：表现像按文件名排，容易误判成「文件名排序 bug」，实际是 date 失效。
- 改完转换器记得删 md 强制重转（`rm content/posts/2026*.md &amp;&amp; sync-site`​），否则只对新增文章生效。
