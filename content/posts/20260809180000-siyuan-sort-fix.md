# 折腾小记：思源笔记里帖子顺序不对的排查

上次发完两篇《折腾小记》，用户发现思源「个人网站」笔记本里这两篇的顺序是反的：圆角那篇（后写的）排到了黑边那篇（先写的）前面。按阅读顺序应该黑边在前、圆角在后，结果思源文档树里是圆角在上。记一下这次的排查，因为真相藏得比预想深。

## 弯路一：看 API 返回，顺序是对的？

第一反应是查思源 API 拿文档树：

```
POST /api/filetree/listDocsByPath
{"notebook": "20260808225839-mm6cxzc", "path": "/"}
```

返回的 files 数组里，两篇折腾小记的 sort 字段是 7 和 8——黑边 7、圆角 8，数字小的在前，看起来**黑边在前、圆角在后**，顺序正确。

但用户说看到的是反的。API 说对、界面说错，矛盾。

## 弯路二：以为是 sort 字段直接决定顺序

sort 字段 7、8 是从哪来的？翻思源数据目录：

```
data/20260808225839-mm6cxzc/.siyuan/sort.json
```

里面有 8 个条目。除了 6 个真实文档，还有两个**幽灵条目**：

```json
{
  "20260808235517-0bxohh4": 3,
  "20260809000318-hel2ph7": 4,
  "20260809002409-yg7kzn6": 5,
  "20260809002656-pz1hdzq": 6,
  "20260809160000-black-edge-fix": 9,
  "20260809174000-corner-bug": 10,
  "20260809174940-c755s9p": 7,
  "20260809174942-31s6rcx": 8
}
```

​`black-edge-fix`​ 和 `corner-bug`​ 是当初 API 创建文档时的旧名字（不是合法文档 ID），思源根本不认它们，纯属干扰项。真实文档 ID 是 `c755s9p`​（黑边）和 `31s6rcx`​（圆角），sort 是 7 和 8。

到这里还是「黑边在前」。为什么界面是反的？

## 真相：排序方式由 sortMode 决定，不是 sort 字段

思源文件树的排序方式是个配置项。笔记本级配置：

```
POST /api/notebook/getNotebookConf
→ sortMode: 15
```

全局配置在 `conf/conf.json`​：`fileTree.sort: 6`​。去思源内核源码（kernel/model/file.go）里查 `ListDocTree`​ 的排序逻辑，`sortMode`​ 有一整套枚举：按名称、按更新时间、按创建时间、按引用数、按自定义排序……`sort=6`​ 是「自定义拖拽排序」，数据源就是 `.siyuan/sort.json`​。

所以 UI 实际按 sort.json 渲染。而 sort.json 里 c755s9p=7、31s6rcx=8，**黑边 sort 7 小于圆角 8，黑边在前**——跟 API 一致啊？

等等，问题出在别处。再看一眼 sort.json：真实文档的 sort 是 3/4/5/6/7/8 连续的吗？不——中间**断了**：`black-edge-fix=9`​、`corner-bug=10`​ 这两个幽灵占了 9 和 10。这说明什么？说明这两篇文档**最初**的 sort 记录是用 slug 名字写的（9、10），后来用 API 重建文档拿到合法 ID（c755s9p、31s6rcx）时又补了 7、8 的条目。历史遗留，但没影响顺序。

那到底谁在作怪？**changeSort 才是真正的排序写入口**。前端拖拽排序后调的就是它：

```
POST /api/filetree/changeSort
{"paths": ["/20260809174942-31s6rcx.sy", "/20260809174940-c755s9p.sy", ...], "notebook": "..."}
```

​`paths`​ 传完整路径数组，顺序即新排序。它会重写 sort.json 并广播刷新。

## 修法：直接调 changeSort 换顺序

目标：圆角（31s6rcx）在前、黑边（c755s9p）在后。把 paths 按新顺序排好调 API：

```json
{
  "paths": [
    "/20260808235517-0bxohh4.sy",
    "/20260809000318-hel2ph7.sy",
    "/20260809002409-yg7kzn6.sy",
    "/20260809002656-pz1hdzq.sy",
    "/20260809174942-31s6rcx.sy",
    "/20260809174940-c755s9p.sy"
  ],
  "notebook": "20260808225839-mm6cxzc"
}
```

调用后 sort.json 自动重排：圆角=5、黑边=6。再调 listDocsByPath 和用无头浏览器实测 UI，顺序都是圆角在前、黑边在后。用户要的顺序，成了。

## 经验

- **思源文件树排序是 sortMode（枚举）驱动**，`sort`​ 字段只是自定义排序模式下的数据，别直接用「sort 小在前」想当然。
- **改排序走 API**（changeSort / 前端拖拽），直接改 sort.json 会被思源覆盖。
- **API 创建文档会在 sort.json 留幽灵条目**（旧 slug 名），不影响显示但会误导排查，看到别慌。
- 界面与 API 返回矛盾时，先确认 UI 用的排序模式（getNotebookConf 的 sortMode），再对症下药。
